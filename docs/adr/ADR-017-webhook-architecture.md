# ADR-017 — Outbound webhook architecture

Status: Proposed
Date: 2026-09-22
Depends on: ADR-012 (public Run API)

## Context

Pipelines and chat integrations want to know when a run finishes without polling. The Run API
makes polling workable, so webhooks are a latency and efficiency improvement, not a new
capability.

A survey of nine E2E testing platforms found the bar here is low. Five of the nine sign nothing
at all. Only one documents replay protection. Only two document a retry policy. Several publish
no payload schema, so no reusable receiver can be written against them. Not one documents a
delivery guarantee strong enough to gate a merge on.

That matters for us specifically. Our webhooks announce runs whose execution involved a decrypted
`storageState` (ADR-004), against environments that may be internal. An unsigned webhook from this
platform is a bigger problem than an unsigned webhook from a visual-diff tool.

## Decision

### Webhooks never gate a merge

The CLI exit code and the Run API are the gate (ADR-012). Webhooks are a notification
side-channel. Say this in the docs rather than leaving a customer to discover it.

### Signing

HMAC-SHA256, keyed with the endpoint's signing secret, over the exact string:

```
{timestamp}.{raw request body bytes}
```

Hex encoded, sent as `X-TestFlow-Signature: sha256=<hex>`. The timestamp is the value of
`X-TestFlow-Timestamp` in Unix seconds.

Signing the timestamp alongside the body, rather than the body alone, is what makes a captured
delivery non-replayable. Receivers reject a delivery whose timestamp is more than **300 seconds**
from now, verify against the raw bytes before any JSON parsing, and compare in constant time. Our
documentation states all three, with sample code, because a signature scheme nobody verifies
correctly is decoration.

Secrets are at least 32 characters, generated by us, shown once, and never returned by the API.

### Key rotation without downtime

An endpoint may hold two active secrets during rotation. We send **space-delimited signatures**,
one per active secret, and a receiver accepts if any verifies. Rotation is then: add a secret,
deploy the receiver change, remove the old secret. No hard cutover.

This follows the Standard Webhooks convention and is the one place the best incumbent scheme is
weak, since it invalidates the previous secret immediately.

### Headers

```
X-TestFlow-Event           run.completed
X-TestFlow-Event-Id        stable across all retries — the dedupe key
X-TestFlow-Event-Version   payload schema version, integer
X-TestFlow-Request-Id      new on every delivery attempt
X-TestFlow-Timestamp       Unix seconds, inside the signed string
X-TestFlow-Signature       sha256=<hex> [sha256=<hex> ...]
Content-Type               application/json
```

We additionally emit `webhook-id`, `webhook-timestamp` and `webhook-signature` per Standard
Webhooks. Emitting both sets costs nothing and lets off-the-shelf receiver libraries work
unmodified.

### Delivery semantics, stated plainly

- **At-least-once.** Receivers must be idempotent, keyed on `X-TestFlow-Event-Id`.
- **No ordering guarantee.** A `run.completed` may arrive before its `run.started`. Receivers
  order by the timestamps in the payload, not by arrival.
- **More than one delivery per run is normal**, because status transitions fire events. One
  surveyed product posts on every status change and gives no explicit terminal marker, so
  consumers can only infer the final post from the presence of a duration field. We instead put a
  `terminal` boolean on every payload, so a receiver never has to guess whether more is coming.
- **Retries:** 10 attempts total, exponential backoff with jitter, spread over roughly 24 hours.
- **Retry on:** transport errors, `408`, `429`, and `5xx`. Honour `Retry-After`.
- **Do not retry:** `3xx` and other `4xx`. A `410 Gone` disables the endpoint and notifies the
  project owner.
- **Per-attempt timeout:** 10 seconds. We read at most the first 8 KB of the response body.
- Test and ping deliveries are never retried.

### Delivery log

The last 100 deliveries per endpoint, showing **every attempt**, not only the last one. A log that
collapses retries into a final state cannot be debugged from, which is a mistake one surveyed
product documents making. Manual redelivery preserves the original `X-TestFlow-Event-Id` so a
correctly built receiver deduplicates it. `Authorization` and `Cookie` headers are redacted in
stored history.

### Destination safety

The destination is resolved and validated **before every delivery**, not once at creation.
Requests to private, loopback and link-local addresses are refused. We do not follow redirects;
the endpoint must respond directly. Deliveries egress through a filtering proxy on its own
network path.

Without per-delivery resolution, an endpoint that passes validation at creation and later resolves
to an internal address turns the webhook sender into a request forwarder into our own network.

### Events and payload

Initial events: `run.started`, `run.completed`, `run.cancelled`, `suite_run.completed`.

Payloads are **flat**, fixed and versioned. Delivery metadata lives in headers, not in the body.
User-templated payloads, which two surveyed products offer, are rejected for v1: they let a
customer hit a third-party API directly, and they destroy the canonical schema that makes a
reusable receiver possible. Templating can be added later without breaking a fixed schema.

`run.completed` carries, at minimum:

```
run_id, run_number, run_url, project_id, suite_id, test_case_id
status, status_reason, has_failures, has_errors
trigger: { source, provider, commit_sha, branch, pr_number, actor, ci_url }
environment_id, base_url_used, viewport, execution_tier
queued_at, started_at, completed_at, duration_ms
totals: { tests, passed, failed, flaky, skipped, quarantined }
retry_summary: { attempts, passed_first_attempt }
artifacts: [ { kind, url, expires_at } ]
```

`has_failures` and `has_errors` are separate booleans, per ADR-012's corrected status model. A
consumer must be able to distinguish "the tests failed" from "we could not run the tests" without
parsing prose.

### Secrets never appear in a payload

No auth profile contents, no `storageState`, no cookie or storage values from the storage
capability, no network mock bodies, no environment variables. Identifiers and non-secret metadata
only. One surveyed product's sanctioned pattern is embedding credentials in the webhook URL
itself, which puts them in every log on both sides. We reject credentials in the URL.

### Limits

Five endpoints per project. Target payload under 20 KB; a run with very many tests sends totals
and a link, never the full per-test breakdown.

## Prerequisites in the TestRun model

These fields must exist **before** webhooks ship, or the first payload is missing what consumers
need and v1 is immediately wrong:

- Trigger provenance as a closed enum, not free text.
- The separate `has_failures` / `has_errors` booleans and a named infrastructure-error state.
- Retry attempt count and whether the run passed on its first attempt.
- Artifact records with their own expiry, since artifacts must outlive the vendor-style link.

## Alternatives considered

- **Poll only, no webhooks.** Defensible, and it is what the survey says every incumbent's gate
  actually does. Rejected because chat and dashboard integrations poll wastefully for an event
  that is rare and bursty.
- **Sign the body only.** What most signing incumbents do. Rejected: without a signed timestamp a
  captured delivery replays forever.
- **User-templated payloads in v1.** Rejected above.
- **Server-Sent Events or a streaming API instead.** Good for the live run view in our own UI, and
  wrong for third-party integrations behind firewalls.

## Consequences

- A delivery subsystem is real work: a queue, a retry scheduler, a delivery log, an egress proxy
  and a rotation flow. It is comparable in size to a small service and should not be estimated as
  "add an HTTP POST after the run finishes".
- Signing documentation with verified sample code in at least two languages is part of shipping
  this, not a follow-up.
- The delivery log holds response bodies from customer endpoints, so it inherits a retention
  policy and a redaction rule.
- We will be ahead of every surveyed incumbent on this surface. That is worth stating in sales
  material, and it only stays true if rotation and the delivery log ship with v1 rather than after.
